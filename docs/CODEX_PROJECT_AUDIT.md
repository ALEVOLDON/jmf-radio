# Отчёт Codex: аудит проекта JMF Radio

**Дата:** 17 августа 2026  
**Статус:** технический и продуктовый аудит без внесения изменений в исходный код.

## Итоговая оценка

JMF Radio — сильный, самобытный интерактивный проект. Это не типовой аудиоплеер, а цельный «виртуальный клуб»: Three.js-сцена, реактивный свет, персонажи, ракурсы камер и визуальный DJ-пульт создают запоминающийся продуктовый образ.

- **Концепция и визуальная идентичность:** 8/10.
- **Готовность к публичной эксплуатации:** около 5.5/10.

Сейчас это убедительный интерактивный прототип и локальная радиостанция. Чтобы безопасно и стабильно публиковать его для аудитории, необходимо укрепить серверную модель, разграничить права и привести заявленные функции интерфейса в соответствие с реализацией.

## Что реализовано хорошо

1. **Чёткая структура клиентского кода.**
   - `src/audio/AudioEngine.js` — воспроизведение, Web Audio API, эквалайзер, кроссфейд и анализ частот.
   - `src/scene/` — независимые подсистемы Three.js: помещение, свет, DJ, бар, танцпол и аудиосистема.
   - `src/ui/UIController.js` — DOM-управление и взаимодействие с интерфейсом.
   - `server.js` — библиотека, метаданные, жанры и аудио-стриминг.

2. **Хорошо сформулированы два сценария использования.**
   - Режим DJ Mix даёт эффект интерактивной аппаратной станции.
   - Radio Mode уменьшает сложность и лучше подходит для мобильного фонового прослушивания.

3. **3D-сцена связана с музыкой, а не служит статичной декорацией.**
   Анализатор частот передаёт данные свету, персонажам, танцполу, экрану и VU-индикаторам; есть набор камер и кинематографический режим.

4. **Серверный фундамент для локальной библиотеки уже есть.**
   Проект сканирует файлы, считывает метаданные, строит очередь, фильтрует жанры и поддерживает HTTP Range-запросы для перемотки аудио.

5. **Сборка проходит.**
   `npm run build` завершился успешно. Vite сообщил лишь о крупном JavaScript-чанке: 600.85 KB после минификации, 150.90 KB gzip.

## Подтверждённые проблемы и риски

### P0 — исправить до публичного запуска

#### 1. Слушатель может управлять общим эфиром

Состояние текущего трека хранится глобально на сервере. При этом открытые методы `POST /api/next`, `POST /api/prev`, `POST /api/genre/select` и `POST /api/rescan` меняют это состояние для всех.

Клиент также вызывает `/api/next` во время переходов. Поэтому один пользователь способен переключать трек, менять жанр или запускать повторное сканирование для остальных слушателей.

**Где:** `server.js`, маршруты API около строк 451–590; глобальные переменные состояния около строк 157–163.

**Что сделать:**

- Разделить публичные endpoint'ы слушателя и защищённые endpoint'ы администратора/DJ.
- Добавить аутентификацию для команд управления.
- Добавить rate limit для изменяющих состояние запросов.
- Не использовать клиентские действия слушателя для изменения глобального эфира.

#### 2. Это пока не синхронное live-радио

Браузер получает отдельный аудиофайл по `/api/stream/:id` и начинает воспроизведение в собственный момент времени. У разных слушателей неизбежно будет разный прогресс. Клиентский Auto-DJ дополнительно вызывает серверный переход треков.

**Последствие:** продукт корректнее называть персональным DJ-плеером над общей библиотекой, а не синхронной радиостанцией для аудитории.

**Что сделать:** выбрать одну модель продукта.

- Для **персонального DJ-плеера** сделать очередь и управление пользовательскими/сессионными.
- Для **настоящего радиоэфира** сделать серверное расписание, синхронизацию по времени и потоковый формат: HLS, Icecast или WebRTC — выбор зависит от задержки и инфраструктуры.

#### 3. `.env` из инструкции не загружается

README предлагает создать `.env` и указать `MUSIC_DIR`, однако `server.js` не использует `dotenv` и не запускается с `node --env-file`. Обычный `npm start` этот файл не читает.

**Где:** `README.md`, `.env.example`, `server.js` строки 12–13.

**Что сделать:**

- Добавить `dotenv` и `import 'dotenv/config'`; либо
- изменить стартовый скрипт на `node --env-file=.env server.js` (при совместимой версии Node.js).
- Обновить `start-radio.bat`, чтобы он не показывал жёстко заданный путь `D:\Soundcloud`.

#### 4. Открытый CORS и отсутствие аутентификации

`app.use(cors())` разрешает обращения со всех origin, а изменяющие API не имеют защиты.

**Где:** `server.js:15`.

**Что сделать:** ограничить разрешённые origin'ы, включить аутентификацию на административных маршрутах и не публиковать сервис через туннель до выполнения пунктов P0.

### P1 — надёжность и безопасность

#### 5. Каждый rescan запускает дополнительный таймер

`initRadio()` создаёт `setInterval(checkTrackAdvancement, 1000)`. `/api/rescan` снова вызывает `initRadio()`, не очищая старый интервал.

**Последствие:** через несколько пересканирований несколько таймеров смогут конкурентно переключать треки.

**Где:** `server.js:316`, `server.js:589`.

**Что сделать:** хранить идентификатор интервала, очищать существующий перед созданием нового, либо запускать его ровно один раз во время старта сервера.

#### 6. Метаданные треков вставляются как HTML

Названия и исполнители из музыкальных тегов используются в `innerHTML` при построении очереди. Вредоносное содержимое ID3-тега может стать XSS в браузере.

**Где:** `src/ui/UIController.js:1301`.

**Что сделать:** создавать DOM-элементы и задавать данные только через `textContent`. Не вставлять внешние или файловые метаданные в шаблонные HTML-строки без экранирования.

#### 7. В Git хранится приватный кэш музыкальной библиотеки

`genre_library_cache.json` содержит абсолютные пути, названия и исполнителей из локальной музыкальной коллекции.

**Что сделать:** удалить кэш из репозитория, добавить `genre_library_cache.json` в `.gitignore` и оставить при необходимости безопасный пример структуры без реальных данных.

#### 8. Обработка HTTP Range недостаточно защищена

`streamAudioFile()` не валидирует начальную и конечную позиции диапазона. Некорректные или выходящие за размер файла `Range`-запросы могут приводить к ошибкам стрима вместо корректного ответа `416 Range Not Satisfiable`.

**Где:** `server.js:488`.

**Что сделать:** валидировать `start`, `end`, порядок байтов и границы файла; подписываться на ошибки `createReadStream`.

#### 9. Кэш метаданных сохраняется неполно

Сохранение кэша планируется через две секунды от `initRadio()`, а метаданные большинства треков подгружаются лениво уже позднее. После позднего чтения метаданных кэш повторно не сохраняется.

**Где:** `server.js:309`, `server.js:217–269`.

**Что сделать:** сохранять кэш после успешного обновления метаданных с debounce, либо выполнять отдельный контролируемый этап индексирования.

### P2 — соответствие интерфейса реализации

#### 10. Часть аппаратного интерфейса пока декоративная

Интерфейс заявляет Sync, hot cues, выбор типа FX, Beat Grid, Browser/Playlist, Record, Split и Auto DJ. Однако у части этих элементов отсутствуют обработчики или реальная логика. Например, Sync-кнопки получаются в `UIController`, но не получают событий; FX ON меняет только CSS-класс.

**Где:** `index.html`, `src/ui/UIController.js`.

**Что сделать:**

- либо реализовать сначала самые заметные функции: Sync, hot cues и фактические FX;
- либо визуально обозначить функции как «скоро»/отключить их, чтобы ожидания пользователя совпадали с поведением.

#### 11. Показатели BPM частично синтетические

При отсутствии надёжных тегов BPM присваивается эвристически; на сервере применяется случайное отклонение BPM. Это выглядит правдоподобно, но не является анализом темпа.

**Где:** `server.js:134`, `server.js:154`; `AudioEngine.js` — fallback BPM.

**Что сделать:** явно обозначать оценочный BPM, либо проводить полноценный офлайн-анализ библиотеки и кэшировать результат.

#### 12. Модели Blender не подключены к веб-сцене

В `public/models` есть GLB-ассеты, а `GLTFLoader` импортирован в `DJCharacter.js`, но загрузчик не используется в коде. Модели копируются в итоговую сборку, однако не участвуют в рендере.

**Что сделать:** либо загрузить модели с контролем качества и LOD, либо удалить неиспользуемый импорт/ассеты из веб-поставки и оставить Blender-файлы как production source.

## Производительность, поддерживаемость и доступность

### Производительность

- Основной JS-чанк превышает порог предупреждения Vite в 500 KB.
- Three.js сцена использует тени, DPR до 2 и значительный объём процедурной геометрии; на слабых мобильных устройствах возможны просадки FPS и нагрев.

**Рекомендации:** динамически импортировать тяжёлую 3D-сцену, добавить профиль low/medium/high, понижать DPR на мобильных, отключать дорогие тени и эффекты при низком FPS.

### Поддерживаемость

- `UIController.js` (~61 KB) и `style.css` (~70 KB) уже велики для единственного модуля/файла.
- В проекте нет тестов, ESLint/Prettier, TypeScript или CI-проверок.

**Рекомендации:** разделить UI по областям (decks, radio, queue, modal, mobile), добавить ESLint + форматирование, минимальные интеграционные тесты API и smoke-тест страницы.

### Доступность и локализация

- У части кнопок есть `title` и `aria-label`, но это покрывает не весь интерфейс.
- Нужна клавиатурная навигация для основных действий и `prefers-reduced-motion`.
- Интерфейс и README преимущественно англоязычные, хотя целевая коммуникация может быть русской.
- Шрифты загружаются из Google Fonts: локальная/offline работа будет визуально отличаться.

## Приоритетный план исправлений

### Этап 1 — безопасный запуск (P0)

1. Подключить `.env` и убрать жёстко заданные пути из batch-скрипта.
2. Ввести роль администратора/DJ и закрыть команды управления.
3. Ограничить CORS.
4. Выбрать: персональные сессии DJ или общий синхронный эфир.
5. Удалить приватный кэш библиотеки из Git.

### Этап 2 — надёжность (P1)

1. Исправить жизненный цикл таймера Auto-DJ/rescan.
2. Валидировать Range-запросы и обработать ошибки потоков.
3. Исправить стратегию сохранения кэша метаданных.
4. Убрать небезопасный `innerHTML` для данных музыкальных тегов.
5. Добавить тесты серверных маршрутов.

### Этап 3 — честный и завершённый UX (P2)

1. Реализовать Sync, hot cues и реальные FX либо скрыть незавершённые элементы.
2. Сделать BPM предсказуемым и явно обозначить способ его определения.
3. Интегрировать или исключить неиспользуемые GLB-ассеты.
4. Оптимизировать 3D-профили для мобильных.
5. Добавить доступность и локализацию.

## Заключение

Главная ценность JMF Radio — узнаваемость и атмосфера. Проект уже выглядит как продукт с собственной сценой и стилем, а не как учебная демка. Следующий качественный скачок даст не ещё один визуальный эффект, а надёжная модель эфира, защита управления и доведение наиболее заметных органов DJ-пульта до реальной работы.
